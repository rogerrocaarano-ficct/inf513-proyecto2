# Stack

**For the agent:** read before writing code. This file is the AI Unified Process record of the technical layers,
independent of how the team documents its architecture. The Layers table says which layer skill builds and tests
each technical layer: `/use-case-implement` runs the Skill column bottom-up, `/use-case-test` runs the Test skill
column from the integration layer up, and `/use-case-coverage` searches for the markers in the last table.

A layer the project does not have is marked `–` in every column (a UI layer in a REST service). The Integration
layer table keeps a row only when the project has that layer — a REST service drops the UI row, a Vaadin Flow
project without a service layer drops the Service row. Its Test skill column names
what the Layers table names for the layer in Tested in (`–` while the skill is not installed). A use
case is tested in the first row its `**Layers:**` line names, or in the first row when it has no such line. That layer's tests run in process against the real database
and exercise every layer below it, so `/use-case-test` runs its test skill and the ones above it and writes no tests
of their own for the layers below unless a run names them (`/use-case-test UC-001 persistence`).

No AIUP layer skill covers Laravel, so every Skill and Test skill cell is `–`: `/use-case-implement` builds each
layer from the project's own conventions and skills (`laravel-best-practices`, `inertia-react-development`,
`wayfinder-development`, `fortify-development`, `tailwindcss-development`), and `/use-case-test` writes Pest tests
following `testing-best-practices`.

The UI layer is server-driven: an Inertia controller validates with a Form Request, authorizes with a Policy, calls
an Action, and renders a React page. Its Pest feature tests run in process against the real database, so the UI is
the integration layer. Inertia is no separate API layer: the controllers serve only the project's own React pages,
and there are no JSON endpoints for other clients. The "API RESTful" of `docs/lineamientos_tecnicos.md` is met by
the Inertia requests between React and Laravel, as C-002 fixes. A use case offered through the service alone (a
scheduled command or a queued job) is tested in the Service layer by calling its Action.

Integration tests run against a local PostgreSQL test database, not SQLite, so that constraints, triggers, and
types of C-008 are exercised for real; the first use case implemented switches `phpunit.xml` to it.

## Module layout

Flat single Laravel application, root namespace `App\`:

- `app/Actions/<Área>/` — one single-purpose Action class per business operation (the service layer), like the
  existing `app/Actions/Fortify/`.
- `app/Models/` — Eloquent models, derived from `docs/entity_model.md`; `database/migrations/`,
  `database/factories/`, `database/seeders/` next to them.
- `app/Http/Controllers/<Área>/`, `app/Http/Requests/`, `app/Policies/`, `app/Http/Middleware/` — the server side
  of the UI layer; routes in `routes/web.php` and `routes/settings.php`.
- `resources/js/pages/`, `resources/js/components/`, `resources/js/layouts/` — the React side of the UI layer;
  route helpers generated by Wayfinder into `resources/js/actions/` and `resources/js/routes/`.
- `tests/Feature/<Área>/` — Pest feature tests per use case; `tests/Unit/` — unit tests of isolated logic.
